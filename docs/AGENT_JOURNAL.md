## 2026-08-30 avond — PR #8 (Phase E): CI-flake-diagnose + review-cycle-les

- **Lesson:** A PR-Piet review of the last push can arrive AFTER the worker turn ends — the thread-check right before the merge signal is mandatory, a "clean" verdict has a shelf life.
  (Live on PR #8: after the last code push `d6ff3e2` there still followed a thread reply + resolve, 2 concurrency-cancels of the pull_request review check, and a fresh review run — an earlier "ready" statement was already stale by the time the next session looked.)
- **Lesson:** CI TimeoutError on a test unrelated to the PR diff: verify flake first (local 3x + pre-PR base + prior runs history), then rerun --failed — never push speculative fixes for un-reproduced failures.
  (Live: 2× the same TimeoutError on 2 different runners vs 9× green locally; the "rerun failed ⇒ regression" inference was wrong — the real cause sat in the test environment, not in the PR diff.)
- **Fact (pre-existing flake, 3e bewijslijn):** de gateway-journal (`guardian-llmprovider-gateway/docs/AGENT_JOURNAL.md`) documenteerde exact deze test al vóór de Phase E-branch — tijdens de caretaker PR #7-cyclus (2026-08-30 middag, suite toen 84 tests): 1 fail in de volle suite, 3× groen daarna, "waarschijnlijk machine-timing (wait_for timeout=2)". De CI-failures in de PR #8-cyclus bevestigen die observatie (zelfde test, zelfde 2s-budget, belasting-afhankelijk op de self-hosted pool). Cross-repo journals lezen vóór een flake-verdict is gratis bewijs.
- **Fact (test isolatie):** de Phase-C/D swap-tests praten via `CARETAKER_SERVER_URL=http://127.0.0.1:11440` (fixture `isolated_paths`) tegen wat er op de runner-host op 11440 luistert — op ai-kvm2 is dat de productie-llama-server (CI-log toont "Backend model mismatch … qwen3.8-27b…"). Op een schone runner weigert de connect direct; op ai-kvm2 hangt het resultaat van de backend-belasting af (2 s `wait_for`-budget). Follow-up-kandidaat: HTTP-mock-backend per test of backend-URL hard isoleren.
- **Fact (test raakt platform-selectie niet):** `test_switch_model_swap_frees_old_slot_without_deadlock` injecteert `FakeServerProcess` via `_make_manager(..., server_process=proc)` — `_default_server_process()` (de Phase-E-wijziging in `manager.py`) wordt in die test nooit aangeroepen. Bij CI-failures in lifecycle-tests eerst de injectie-path checken vóór je de platform-selectie verdenkt.
- **Fact (workflow):** een rerun van een concurrency-gecancelde pr-piet-run kan opnieuw gecanceld worden door een nieuwere run in dezelfde concurrency-groep (20:03:19: de rerun-tier-1 werd gecanceld door verse `pull_request`-run `33332549005`, gestart 20:03:08). Check altijd op nieuwere runs in de groep vóór je concludeert dat een rerun "mislukt".
- **Fact (PR-Piet triggers):** de workflow draait op élke `issue_comment` (`types: [created, edited]`) en behandelt non-slash-comments als onbekende commands — tier-1 faalt dan met exit 3 ("Unknown command: …", "geen verse review (lege model-output)") zónder een review te posten. Vrije merge-signal-/slot-comments genereren dus rode runs: hinderloos voor de merge-state (comment-runs hangen niet aan de head-check-rollup), maar verwacht ze in de run-lijst en vermeld ze in het merge-signaal.

## 2026-09-25 — Comfy-lifecycle live op windows-host: idle-stop + wake-proxy + llama-sleep bewezen (PR #11) — DSH agent (glm-5.3-flash)

- **De spec van de operator, end-to-end bewezen:** llama idle 5 min → `is_sleeping: true` + de VRAM 13,2→4,3 GB → een request → antwoord in 7,5 s + `is_sleeping: false` + de VRAM terug. Comfy: de idle-stop via de poort-kill ✓, de 8188-connect → de GPU-first-wake → comfy op 8189 → HTTP 200 door de wake-proxy ✓. De STT-cold-start via de caretaker ✓ (pid bewezen).
- **LLAMA-SLEEP = GEEN CODE:** de windows llama-binary (b10964) heeft `--sleep-idle-seconds N` — een config-regel in de models-local-`extra_args`. De server slaapt zichzelf uit VRAM en wekt bij het volgende verzoek zelf. `is_sleeping` in `/props` = het bewijs-signaal.
- **COMFY-STOP-LES:** `schtasks /End` doodt de task-instantie maar het comfy-python-proces OVERLEEFT (geen job-object) → een zombie op 8189 blokkeert de volgende wake. De stop-command = een poort-kill (`D:\stop-comfy.ps1`: Get-NetTCPConnection 8189 → Stop-Process).
- **COMFY-START-LES:** comfy's CUDA-init hangt/crasht bij de VRAM-wedloop met llama/TTS/STT. De start-command = `D:\start-comfy.ps1`: eerst de caretaker-unload (llama) + de tts/stt-release, dán `schtasks /Run`. Deterministisch GPU-first, hetzelfde patroon als TTS_STOP_LLAMA=1.
- **NSSM-ENV-DISCIPLINE (3 recoveries):** `nssm set AppEnvironmentExtra <lijst>` VERVANGT de hele lijst — een read-modify-write via `nssm get` is dodelijk: nssm get wrapt lange values over regels (lege regels = de wrap-markers) en de gefilterde re-set verloor de rest van de env. DE REGEL: de volledige var-lijst altijd expliciet in één `set` (script-based, `D:\set-full-env.ps1` als de actuele waarheid).
- **De actuele windows-env (19 vars):** CARETAKER_KEY (+HOST=0.0.0.0), PYTHONPATH=J:\LLMSTUFF\caretaker-llamacpp\.deps (de deps = `pip --target=.deps`; de --user-site = onyou, onzichtbaar voor LocalSystem!), LLAMA_SERVER_BINARY=J:\LLMSTUFF\llama.cpp\llama-server.exe (de default = het linux-pad → WinError 2 op de ensure!), CARETAKER_LLAMA_SLOTS_DIR=J:\LLMSTUFF\llama_slots (de LocalSystem-home bestaat niet → de llama weigerde `--slot-save-path`), de TTS/STT COMMAND/CWD/URL-knobs, de COMFY-knobs. De oorspronkelijke env = verloren door de eerste set; gereconstrueerd uit boot-ensure.cmd (de key), de qwen3tts-http-registry-parameters (de TTS-command) en de journal.
- **De achterliggende oorzaak van de crash-loop:** de service draait als LocalSystem; de deps in de --user-site van onyou zijn onzichtbaar. `AppThrottle=0` gezet na de throttle-pauzes.
- **Charter-afwijking bewaakt:** de wake-proxy = een lifecycle-trigger (de proxy-pomp = stateless TCP), geen inference-proxy; de idle-beslissing voor comfy blijft host-lokaal (het gateway heeft geen comfy-bewustzijn).

## 2026-09-25 — Watchdog-wiring geïmplementeerd; audit + delegation-les — DSH agent (glm-5.3-flash)

- **Fact (slaap-semantiek):** llama.cpp's eigen unit-test (`tools/server/tests/unit/test_sleep.py`) bewijst: tijdens `--sleep-idle-seconds` slaap antwoorden `/health` en `/props` beide 200 (`is_sleeping: true`); alleen een generatie-request wekt de server. Gevolg: de watchdog's health-probe is slaap-veilig by design — géén speciale behandeling nodig, wél gedocumenteerd in de code zodat niemand hem later "fixt".
- **Fact (ruff-drift):** ruff 0.16.5 default-select flagt 21 pre-existing bevindingen in comfy/tts/stt (I001/S110/ASYNC230/SIM115/SIM102/PLW0602/UP041/RET501/RUF059) terwijl CI groen is → de CI-ruff-versie is anders (laxer/ouder) dan lokaal. De 2026-08-29-voorspelling ("een toekomstige ruff neemt meer regels in de default") is inkomen. Volg-item: ruff pinnen in de reusable-CI of een opkuis-pass.
- **Fact (suite-duur):** de volledige suite (173 tests) duurt lokaal ~143 s (STT/TTS VRAM-gate-polls domineren). Foreground-bash-runs met 60-300 s-timeout killen hem "geruisloos" (geen output bij kill — buffers). Les: suite draaien met log-naar-bestand (`> /tmp/x.log 2>&1`) zodat een kill/timeout het voortgangsbewijs laat staan.
- **Lesson (delegation):** een subagent kan "running" blijven terwijl hij MinutenLang geen artifacts produceert; pycache-mtimes bleken een dubieus levendigheidssignaal (zelfde 3 bestanden telkens "recent"). Na 4 ronden zonder artifacts: interrupt + inline takeover (het volledige ontwerp lag al klaar) — 6 pins + wiring in één pass af. Eskalatie-afsprake vóóraf maakte de beslissing triviaal.
- **Fact (audit):** alle drie de inter-repo handoffs (watchdog 2026-09-16, backend-key 2026-09-11, OOM 2026-09-09) waren nergens geïmplementeerd; geen stash, geen losse werk-branches, geen dirty .py op de deploy-kopieën. teams-host's `models.local.settings.yaml`-comment noemt `--api-key` maar de echte `extra_args` zijn keyless (stale comment — opruimen bij de volgende windows-touch).
- **Review-les (PR #12 ronde 1, 1 terecht):** het fail-open-contract van de lifespan dekte alléén de manager-constructie, niet de `start_watchdog()`-arming zelf — een raisende arming zou de boot alsnog geblokkeerd hebben. Losering: één try om constructie + arming; pin `test_lifespan_survives_raising_start_watchdog`. Les: een fail-open-claim dekt de HELE arming-pad, niet alleen het eerste haalbare faalpunt.
- **Review-les (PR #12 ronde 3):** `float(raw)` accepteert `"inf"`/`"infinity"`/`"nan"` — een knob-waarde die de watchdog's sleep/backoff-rekene stil platlegt (asyncio-slaapt eeuwig of gooit op NaN). Fix: `math.isfinite(value) and value > 0`-validatie met warning + default; pin `test_lifespan_falls_back_to_default_on_non_finite_or_non_positive`. Les: numerieke env-validatie = parse + finite + range, altijd.
- **Fact (review-mechaniek):** `gh pr view --json reviews` sorteert NIET op tijd — `reviews[0]` is de óudste; de pr-agent-review-state-JSON per review bevat head_sha + per-finding `state` (ACTIVE/...) — altijd die parsen, niet de review-state-enum vertrouwen (COMMENTED kan óók ACTIVE findings bevatten).
- **Fact (pr-piet clean-sweep):** de reusable runt na de review een "clean-sweep" die pr-agent "PR Reviewer Guide"-"[Persistent review]"-sporen verwijdert — een geslaagde review kan dus ZICHTBAAR onzichtbaar zijn (geen review in de API terwijl de run success was). De autoritative verdict staat in de tier-1 job-log ("Full_response": `key_issues_to_review: []` = schoon) + de job-outputs. PR #12 ronde 4: key_issues [] op de code-head.
- **Fact (venv):** het lokale venv is Python 3.14.3 (niet 3.12 zoals CI); `python -m caretaker` importeert de repo-code via cwd, dus de systemd-service draait exact de git HEAD-code.
